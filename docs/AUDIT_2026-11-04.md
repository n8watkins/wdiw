# WDIW audit and next steps (2026-11-04)

WDIW (working name, "What Did I Watch?") is a local-only Manifest V3 Chrome extension that measures your own YouTube watching per channel.
This audit checks what works, how it is built, whether the local-only claim holds, its security and UX against the owner's app quality bar, and how it should relate to TL;DW.
It ends with a recommendation, a short roadmap to a first useful version, naming, and what to do now versus later.

Owner context: "wdiw seems like it would be a decent app to build as an extension of TL;DW, so I don't want to immediately get rid of it; it's just less of a priority."

## Summary

- The code is in good shape: typecheck clean, 145/145 unit tests pass, the production build is 46 kB gzipped for the dashboard bundle and 1.5 kB for the content script.
- The built extension loads in Chromium with no console errors, and the background recorder, dashboards and popup work end to end with seeded data.
- The local-only claim holds for watch data: no `fetch`, XHR, beacon or socket in source, and the only network code in the bundle is Vite's same-origin module-preload helper.
  One nuance: the dashboards load channel avatar images from YouTube's image CDN, so "nothing leaves your device" should be worded more precisely.
- Security: all 23 open Dependabot alerts (2 critical, 7 high) were in dev-only build and test tooling; runtime dependencies are React, React DOM and TanStack Virtual with no alerts.
  PR #5 aligns the toolchain with TL;DW and brings `npm audit` to 0.
- The one load-bearing unknown is unchanged since June: capture has never been run against real YouTube in a real Chrome.
- The UX is a solid dark dashboard but misses several quality-bar items: no responsive layout, dark only, a few visible styling bugs, em dashes in the product name, and the Shorts differentiator hidden behind "All-time".
- Recommendation: keep WDIW as its own small extension in the TL;DW family, not a TL;DW feature; finish a dogfood v1.1 when it is next picked up, and do only the free hygiene now.

## 2. Architecture

- Stack: TypeScript, Vite with `@crxjs/vite-plugin`, React 18 for the popup and options page, a vanilla TypeScript content script, Vitest.
- Data flow: `src/content/watchtime.ts` watches the `<video>` element, counts only forward, visible, non-ad playback through the pure gate in `src/lib/watchgate.ts`, and sends a `WATCH_PROGRESS` delta about every 10 s; `src/background/index.ts` clamps it and calls `recordWatchProgress` in `src/lib/storage.ts`, which updates history, lifetime stats and per-channel stats under one write lock.
- Storage: `chrome.storage.local` keys `tldwStats` (never pruned, bounded maps), `history` (pruned by limit and age, hard cap 5000) and `settings`.
- UI: options page with Stats, Channels, History and Settings sections (hash routed, `#channels` and so on) and a popup "today" card with a Shorts-limit banner and a pause toggle.
- Pure logic lives in `src/lib/*` with tests next to it; React components have no tests.
- Code was copied from TL;DW by design (two repos, no shared package); `PLAN.md` names the YouTube DOM scraper as the one piece worth sharing if drift hurts.

## 3. Code quality

Strengths:

- Pure, well-tested analytics layer (engagement, Shorts sessions, windowing, migration parsers), with comments that explain why, not what.
- Careful concurrency: deltas are claimed before the async send and returned on failure, and `recordWatchProgress` is atomic.
- Bounded storage everywhere (500 channels, 366 days, 5000 history entries).
- Defensive background: message deltas clamped to 0-3600 s, non-finite values dropped.

Weaknesses:

- No ESLint (TL;DW has a zero-warning ESLint gate), no UI or E2E tests, no React error boundary.
- Copied TL;DW leftovers: `scoreToVerdict` in `src/lib/constants.ts:68` is unused, `sawSummary` is always false, storage keys are still `tldw*`.
- Storage write failures are swallowed (`catch {}` in the background listener), so a full quota would silently stop tracking; the popup "Last tracked" line is the only signal.
- Docs drift: `HANDOFF.md` says both that `npm run build` is plain `vite build` and that it bumps the version and copies to Windows (the second is true), and it tells agents to add a `Co-Authored-By` trailer, which the owner's rules now forbid.
- Versions used caret ranges and a crxjs beta range; PR #5 switches the toolchain to exact pins like TL;DW.

## 4. Data and privacy (local-only claim)

Verified:

- Permissions are `storage` plus `https://www.youtube.com/*`; no `tabs`, `scripting`, `history`, `identity` or remote hosts (`src/manifest.config.ts`).
- No network calls in source: no `fetch`, `XMLHttpRequest`, `sendBeacon`, `WebSocket`, `eval` or dynamic remote import.
- In the built bundle the only `fetch` is Vite's module-preload polyfill, which fetches the extension's own files.
- No analytics, telemetry or error reporting SDK; no remote code.
- Takeout and backup imports are read with `file.text()` in the options page and never leave it.
- Uninstalling deletes `chrome.storage.local`; Settings has "Clear watch data".

Nuances to fix in wording or code:

- The dashboards render channel avatars with `<img src>` pointing at YouTube's image CDN (`StatsSection.tsx:210`, `ChannelsSection.tsx:124`), so opening the dashboard makes requests to Google for the channels you watched.
  The watch data itself is not sent, and Google already knows what you watched on YouTube, but "nothing ever leaves your device" is not literally true.
  Either cache avatars as small data URLs at capture time or reword to "your watch data never leaves your device".
- The build exposes two content-script chunks as `web_accessible_resources` to youtube.com with `use_dynamic_url: false` (added by crxjs), which lets YouTube detect the extension; set `use_dynamic_url: true` if crxjs allows it.
- The default history settings (keep 100 entries, delete after 30 days) mean the Channels and History views are a recent window, while Stats is lifetime; the UI says so, which is honest.

## 5. Security

- Dependabot: 23 open alerts on 2026-11-04 (2 critical in tinypool and vitest, 7 high in vite, postcss, nanoid, browserslist and source-map-js, the rest medium or low), all with `scope: development`.
  None reaches the shipped extension; the realistic exposure was the Vite and Vitest dev servers on the owner's machine.
  PR #5 fixes all of them (`npm audit`: 0).
- Message handling: only the extension's own contexts can message the worker (no `externally_connectable`), and the payload is clamped; a hostile youtube.com page cannot reach `chrome.runtime` from the main world.
- The content script reads YouTube DOM text into storage and React renders it as text, never as HTML (no `dangerouslySetInnerHTML`).
- Import parses untrusted JSON with `JSON.parse` and validates shape; there is no file size limit, so a very large Takeout file could freeze the options tab (a real Takeout `watch-history.json` is often 20-100 MB).
- Repo hygiene: a quick grep of the full history found no API-key patterns; commit author is the owner's personal email; a proper secret scan is still required before any visibility change.

## 8. How WDIW fits with TL;DW

- TL;DW (`n8watkins/tl-dw`, public, version 1.1.3) summarizes a YouTube video with Gemini or sends it to ChatGPT, Claude or NotebookLM; it is in an Unlisted Chrome Web Store soft launch with bring-your-own-key Gemini.
- They were one extension until June 2026; `tl-dw/docs/ANALYTICS_SPLIT.md` records the split, and TL;DW's `STATUS.md` now states it "does not track watch time or engagement".
- Shared code: none at runtime; WDIW copied the watch-time engine, engagement logic, storage helpers, dashboards, `VirtualList`, `ConfirmDialog` and the Vite/crxjs setup.
  TL;DW has since moved on (ESLint, Playwright E2E, release-kit, store packaging, exact pins), and WDIW has not followed.
- Data: chrome.storage is per extension, so they cannot share storage; WDIW imports TL;DW's History export (`{ source: "TL;DW", entries }`), but current TL;DW history no longer carries watch durations, so that import now brings titles and channels only.
- Accounts: neither has accounts or servers.
- Brand: TL;DW uses a purple play-style icon and the name "TL;DW"; WDIW uses a similar purple play icon, the same dark palette, and a "What Did I Watch?" tagline that mirrors "Too Long; Didn't Watch".
- Permissions differ sharply: TL;DW needs `scripting`, `contextMenus`, `clipboardWrite`, Gemini and Google AI API hosts and optional chat-site hosts; WDIW needs only storage and youtube.com.

## 9. Options

| Option | For | Against |
|---|---|---|
| A. Merge into TL;DW as a feature (a "Your watching" tab) | One install and one store listing; reaches TL;DW users; one codebase for the YouTube scraper and toolchain. | Reverses a deliberate split; breaks TL;DW's single-purpose story ("summarize this video") and its "does not track watch time" statement; always-on watch tracking inside an extension that holds an API key and wide permissions weakens the local-only trust pitch; adds risk to TL;DW's store review during its soft launch. |
| B. Separate extension in the TL;DW family (recommended) | Keeps a two-permission, trivially reviewable, local-only extension; clean store single purpose; can borrow TL;DW's toolchain, E2E and release setup; can later talk to TL;DW by opt-in messaging. | Two listings to maintain; code copied twice until the scraper is shared. |
| C. Keep standalone with no TL;DW ties | Simplest. | Loses the brand and distribution link that makes it worth building ("companion to TL;DW"). |
| D. Retire | No upkeep. | Owner wants to keep it; the code is nearly complete. |

## 10. Recommendation

Choose B: keep WDIW as its own extension, branded and engineered as part of the TL;DW family, at low priority.
"Extension of TL;DW" fits best as a family relationship: same look, same toolchain and release flow, cross-links in each other's popups, and later an opt-in bridge where TL;DW can ask WDIW "how much of this channel do I usually finish?" through `chrome.runtime.sendMessage` to WDIW's ID with `externally_connectable`.
Merging (A) is worth revisiting only if TL;DW ever needs watch data for its own core feature, and even then a bridge gives that without merging.

## 11. Roadmap to a first useful version (v1.1, "dogfood")

Goal: the owner uses it daily in real Chrome for two weeks and trusts the numbers.

1. Merge PR #5 (toolchain, 0 audit findings).
2. Live verification in the owner's Chrome: load unpacked, watch long videos and Shorts, check per-channel time, the Shorts limit badge and "Last tracked"; fix selectors in `getChannelInfo`, `getVideoMeta` and `isAdShowing` if YouTube changed.
3. Add a Playwright E2E like TL;DW's: build, load under xvfb, drive a local fixture page that mimics YouTube's watch and Shorts DOM, assert storage; this also guards the DOM selectors.
4. Import the owner's real Google Takeout file; add a size guard and a progress state.
5. Fix the four visible UI defects in section 6, add a responsive breakpoint, move the Shorts card into the default view, and fix the "usually" label.
6. Hygiene: ESLint like TL;DW, remove TL;DW leftovers, surface storage write failures, replace em dashes in product copy, refresh `HANDOFF.md`.

After v1.1, if it earns daily use:

7. Store readiness: rename (section 12), privacy wording on avatars, `use_dynamic_url`, drop the redundant host permission, adopt release-kit and TL;DW's package and validate scripts, screenshots, then an Unlisted listing like TL;DW's.
8. Product: rising and fading channels over time, a light theme, a "Download my data" button in Settings, then the opt-in TL;DW bridge.

## 12. Naming

- "WDIW" is a working name: it mirrors TL;DW nicely, but it is hard to say, hard to search, and the current display name contains an em dash.
- Keep the family link and fix the form: "WDIW: What Did I Watch?" works as a stopgap.
- For a store name, `NAMES.md` already shortlists Attune, Tally and Watchpulse; none was checked for Chrome Web Store collisions, domains or trademarks in this audit.
- Avoid "Tube" or "YouTube" in the brand name; "for YouTube" as a descriptor is fine.
- Decide the name before the store listing (step 7), not now.
